# ADR-0001：采用本地桌面应用、会话索引与 Excel COM 自动化

- 状态：已接受（MVP）
- 日期：2026-08-11
- 决策者：项目所有者
- 关联文档：[产品需求文档](../../PRD.md)

## 背景

产品需要在 Windows 上搜索一个或多个可信 Excel 文件，支持多关键词 AND / OR、精确匹配和包含匹配，预览命中单元格所在的完整物理行，并将结果另存为新的 Excel 文件。

关键约束如下：

- 文件内容必须留在本机。
- 工作表的表头和数据区域不固定，一张工作表可能有多个独立表格。
- 源文件不可被修改。
- 不设置人为的文件大小和行数上限，处理过程必须可显示进度和取消。
- 导出应尽可能保留 Excel 格式、公式和工作簿对象。
- 用户本机为 Windows，并安装 Microsoft Excel。

单独使用 `openpyxl` 容易在保存复杂工作簿时改变或丢失 Excel 专有对象；完全通过 COM 逐单元格搜索则会产生大量跨进程调用，性能和可测试性较差。因此需要将 Excel 文件访问、搜索和界面职责分离。

## 决策

采用单机、离线的 Python 桌面应用，并按以下方式划分架构：

1. 使用 PySide6 构建桌面界面。
2. 使用 `pywin32` 调用 Microsoft Excel COM，负责工作簿读取和结果导出。
3. 导入阶段通过 COM 按工作表、按行块批量读取 `UsedRange`，禁止逐单元格跨进程读取。
4. 将读取结果标准化后写入本次应用会话专用的 SQLite 临时索引。
5. 搜索、组合匹配、去重、排序和预览只访问索引，不在每次查询时重新遍历 Excel。
6. 导出阶段重新通过 COM 打开源文件，以只读方式复制所需内容并保存到用户选择的新路径。
7. 所有耗时任务在后台工作线程执行；界面线程只负责交互、进度、取消和结果展示。

高层数据流如下：

```text
用户选择文件
    -> Excel COM 只读、分块读取
    -> 标准化单元格值
    -> 会话级 SQLite 索引
    -> 搜索引擎执行 AND / OR 与精确 / 包含匹配
    -> PySide6 预览
    -> Excel COM 导出新文件
```

## 组件边界

### UI 层

负责：

- 文件选择和已选文件状态。
- 关键词录入和删除。
- AND / OR、精确 / 包含选项。
- 处理进度、取消、错误和结果预览。
- 调用 Windows 保存文件对话框。

UI 层不得直接持有 Excel COM 对象，也不得包含 SQL 查询或匹配规则。

### 应用服务层

负责协调以下用例：

- 准备文件。
- 执行搜索。
- 取消当前任务。
- 导出结果。

应用服务通过接口调用 Excel 适配器、索引仓库和搜索服务，使核心搜索逻辑可以脱离 Excel 安装环境进行单元测试。

### Excel 适配器

负责：

- 创建独立 Excel 实例，而不是复用用户正在操作的 Excel 实例。
- 以只读方式打开源文件。
- 禁止宏自动执行、外部链接自动更新和交互式提示。
- 枚举工作簿、工作表和已使用区域。
- 按块批量读取单元格值、公式结果及必要元数据。
- 在导出时调用 Excel 原生复制和保存能力。
- 在成功、失败或取消后可靠关闭工作簿并退出自动化实例。

COM 对象只允许在创建它的专用工作线程内使用。该线程必须初始化并释放 COM apartment，不允许把 COM 引用传递给 UI 线程或其他工作线程。

### 索引仓库

使用 SQLite 保存本次会话所需的最小数据：

- 来源文件的稳定会话标识和文件路径。
- 工作表名称及顺序。
- 原始物理行号、列号和工作表已使用列边界。
- 单元格的预览值、标准化值和必要的类型信息。
- 文件修改时间及大小，用于检测准备期间文件是否发生变化。

索引数据库默认放置在应用临时目录，正常退出时删除。索引不保存样式、图片或工作簿对象；这些内容仅在导出时由 Excel 从源文件复制。

SQLite 查询实现必须使用参数绑定，不拼接用户输入。精确匹配应使用标准化值索引；包含匹配首版允许扫描会话索引，后续根据真实文件规模决定是否引入 FTS 或其他子串索引。

### 搜索服务

搜索服务不依赖 PySide6、COM 或具体 Excel 文件格式，负责：

- 单元格显示值标准化。
- 精确匹配和包含匹配。
- 同一物理行内的 AND / OR 组合。
- 同一物理行去重。
- 按来源文件、工作表和原始行号排序。
- 返回命中关键词及命中列，供预览和导出追溯。

AND 的语义为“全部关键词出现在同一物理行”，不同关键词可以命中该行的不同单元格。OR 的语义为“至少一个关键词出现在该物理行”。

## 文件处理生命周期

1. 用户选择文件后，应用记录文件路径、大小和修改时间。
2. 后台 Excel 线程以只读、无链接更新方式打开文件。
3. 每次读取有限数量的行并提交给索引仓库，避免将整个工作簿同时保存在内存。
4. 每处理一个块后报告进度并检查取消标志。
5. 单个文件失败时回滚该文件尚未完成的索引数据，并继续处理其他文件。
6. 搜索只针对已成功完成准备的文件。
7. 导出前重新检查源文件大小和修改时间；若发生变化，要求重新准备或明确提示结果可能已过期。
8. 应用退出后删除会话索引和其他临时文件。

读取块的实际行数属于性能参数，由基准测试决定，不写死在业务规则中。

## Excel 自动化约束

实现必须满足：

- 使用独立的 Excel 自动化实例。
- `Visible` 默认关闭。
- `DisplayAlerts` 默认关闭，并在需要用户决定的错误上转化为应用内提示。
- 打开文件时使用只读模式，且不更新外部链接。
- 自动化期间强制禁用宏执行，不依赖用户当前的 Excel 宏设置。
- 不调用源工作簿的 `Save` 或 `SaveAs`。
- 导出只写入用户选择的新路径；同名文件覆盖必须由保存对话框明确确认。
- 所有 COM 引用在 `finally` 路径释放，随后关闭工作簿并退出独立 Excel 实例。
- 不使用强制结束所有 Excel 进程的方式清理资源，以免影响用户正在打开的工作簿。

## 数据与匹配约束

- 搜索范围基于每张工作表的有效已使用区域，而不是 Excel 的整张百万行网格。
- 不推断表头和独立表格边界；命中单位始终是工作表中的物理行。
- 空单元格不写入索引。
- 同一行命中多次只生成一个行级结果。
- 首版不区分英文大小写，关键词两端空白不参与匹配。
- 日期、数字格式、公式结果和 Excel 显示文本之间的标准化细节由独立决策或技术规格确定。
- 隐藏工作表、隐藏行列及公式文本是否进入索引，暂按 PRD 待确认项处理。

## 导出边界

本 ADR 只确定“通过 Excel COM 导出到新文件”，不决定以下格式策略：

- 抽取模式：仅复制命中物理行。
- 原貌模式：复制完整工作表，并隐藏或筛除未命中行。

跨行合并、条件格式区域、图表数据源、数据透视表及跨行公式会使两种策略产生不同结果。默认导出策略必须在真实样本原型验证后通过单独 ADR 决定。

## 考虑过的方案

### 方案 A：仅使用 openpyxl

优点：

- 不要求安装 Excel。
- API 直接，自动化进程管理较简单。
- 适合普通 `.xlsx` 数据读取和单元测试。

缺点：

- 不能由 Excel 原生引擎计算公式。
- 对宏、外部链接、数据透视表、图表、形状及部分条件格式支持不完整。
- 保存复杂工作簿时难以承诺高格式保真。

结论：不采用为主路径。未来可作为无 Excel 环境的受限读取适配器，但不属于 MVP。

### 方案 B：所有搜索都通过 COM 逐单元格执行

优点：

- Excel 是唯一的数据解释来源。
- 实现早期原型较直接。

缺点：

- 跨进程调用次数随单元格数增长，性能差。
- Excel 进程需要在每次搜索期间保持活动。
- 匹配逻辑与 COM 强耦合，不易测试和优化。

结论：不采用。COM 仅用于批量读取和保真导出。

### 方案 C：使用 pandas 读取、搜索和导出

优点：

- 表格过滤和组合条件实现简单。
- 对规则化数据分析友好。

缺点：

- 假设数据具有较规则的表头和二维表结构，与当前输入不符。
- 内存占用较高。
- 导出无法保留原始 Excel 的复杂格式和工作簿对象。

结论：不采用。

### 方案 D：仅在内存中建立索引

优点：

- 实现简单，无临时数据库生命周期。
- 小文件搜索速度快。

缺点：

- 大文件和多文件场景下内存占用不可控。
- 难以满足“不设置人为大小限制”的产品方向。
- 失败恢复和分批提交能力较弱。

结论：不作为默认实现；测试可使用内存仓库替代 SQLite。

## 结果

### 正面结果

- 文件和索引完全留在本机，满足隐私要求。
- 搜索不依赖固定表头或数据区域。
- 批量 COM 读取减少跨进程开销，重复查询无需重开 Excel。
- SQLite 将容量主要转移到磁盘，内存使用更可控。
- Excel 原生导出提供最高可行的格式保真度。
- 搜索逻辑与 Excel 自动化解耦，可独立测试。

### 负面结果

- 应用仅面向 Windows，并依赖已安装的 Microsoft Excel。
- 需要处理 COM 线程模型、Excel 弹窗、进程生命周期和文件占用，开发复杂度较高。
- 首次准备大文件需要时间和临时磁盘空间。
- 包含匹配在没有专用子串索引时可能需要扫描大量索引记录。
- Excel 的已使用区域可能因历史格式残留而异常膨胀，需要后续定义有效范围裁剪策略。

### 风险与缓解

- Excel 进程残留：集中管理 COM 生命周期，并覆盖成功、失败、取消路径的集成测试。
- UI 卡死：所有 COM、索引和搜索任务均放入后台线程，并提供取消标志。
- 临时索引泄露：仅存本地临时目录，默认退出删除，不记录单元格内容到日志。
- 源文件变化：准备和导出阶段比较文件元数据，变化后使结果失效。
- 格式保真不足：在确定导出模式前使用真实复杂样本完成原型验证。
- 超大 UsedRange：按块读取并记录遥测级耗时数据，但日志不得包含文件内容或关键词。

## 验证要求

实现前或实现过程中需要完成：

1. 使用普通表格和复杂格式样本验证 COM 分块读取结果。
2. 对 10 万行及更大样本测量准备时间、索引大小、精确匹配和包含匹配耗时。
3. 验证取消导入、取消搜索和取消导出不会修改源文件或残留 Excel 实例。
4. 验证单文件失败不会污染其他文件的索引结果。
5. 验证 Excel 已由用户打开、文件只读、文件被占用和保存路径无权限时的行为。
6. 对格式导出的两种候选模式制作原型，并形成下一份 ADR。
